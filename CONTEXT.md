# Domain language

Concepts that show up across the codebase. Keep this list short — only terms that mean something specific to maintainers, not generic web/Discord terms.

## Crosspost pipeline

- **Crosspost** — Discord's "publish" action on an announcement-channel message. Limited to 10/hour/channel by Discord.
- **Proxy** — single service that owns all Discord REST traffic. Two responsibilities: (1) async crosspost queue with `POST /crosspost/:c/:m` (ACK in <100ms), (2) generic Discord REST passthrough at `/api/*` used by the bot's discord.js. Single `@discordjs/rest` instance shared by both paths; `BurstHandler` lets interactions bypass the crosspost queue naturally.
- **Gate** — synchronous pre-checks the proxy runs before queueing or processing a crosspost. Order: `invalid_requests` (system shed) → `blocked` (cached denylist) → `sublimit` (per-channel 10/hr counter).
- **Sublimit** — Discord's per-channel 10/hour crosspost limit. Mirrored as a Redis counter (`SublimitCounter` DB). Different from a regular route 429.
- **Blocked channel** — a channel where Discord refused crosspost with 401/403 (missing permission, channel deleted). Cached in `BlockedChannels` Redis DB with 1h TTL. Bot can `DELETE /internal/blocked/:c` to clear when permissions are restored.
- **Invalid request budget** — Cloudflare bans an IP after 10k 401/403/non-shared-429s in 10 min. Proxy self-sheds at 5k to stay well under. Tracked in-memory in the proxy (not Redis); counter sourced from `@discordjs/rest`'s `RESTEvents.Response` event, filtered to exclude shared 429s per Discord docs.
- **Passthrough** — proxy's `/api/*` route that forwards generic Discord REST calls on behalf of the bot. Selective header forwarding (`Content-Type`, `x-audit-log-reason`); body forwarded only when `content-length > 0` or `transfer-encoding` is set.

## Allowlist / registration model

- **Registered channel** — a channel a user opted into auto-publishing via `/ap enable`. Persisted in Postgres `channels` table and mirrored in `Channels` Redis cache (`channel:{id}` keys, value = `{filters, filterMode}` JSON, no TTL).
- **Candidate channel** — an announcement channel offered in the dashboard as an enable-able option. Sourced **live from Discord** (`GET /guilds/:id/channels`, filtered to `GuildAnnouncement`), NOT from the DB — this list is what "appears in the dashboard". Each candidate carries an `enabled` flag = whether a serving [[Registered channel]] row exists (a [[Paused channel]] reads `enabled: false`). Distinct from a registered channel: a candidate can exist with no DB row (never enabled), and a registered row can outlive its candidate (channel deleted in Discord). Cached ≤5 min ([[Dashboard read caching]]) but actively evicted when the bot sees a channel created / deleted / cross the announcement-type boundary, so membership changes surface without the TTL wait.
- **Migrated guild** — a guild that has opted into the v7 allowlist model. Source of truth: `guild.migratedAt` in Postgres (`NULL` = legacy); the `MigratedGuilds` Redis DB (`migrated_guild:{guildId}` = '1', no TTL) is a derived hot-path cache rebuilt at startup. Set on first `/ap enable` or new guild join. Migrated guilds enforce the allowlist; legacy (unmigrated) guilds auto-publish all announcement channels. Migration state is temporary — column and Redis DB are dropped together ~6 months after v7 ships.
- **Bot presence (per edition)** — record of "this edition's bot is in this guild": `bot_presence` table, pk `(guildId, edition)`, `leftAt IS NULL` = in guild. Unrelated to Discord's *user* presence (online status). Replaces the old `guild.deletedAt` semantics (ADR 0006). Drives dashboard per-edition bot state (`freeBotPresent`/`premiumBotPresent`) and the premium revocation backstop. Kept honest by per-edition reconciliation sweeps.
- **Managing edition** — the edition whose bot is doing the publishing: premium once the handover has swapped (or when it is the sole bot), free otherwise — including while a premium handover is pending. Routes backend Discord REST to the right proxy and picks the dashboard's managed view. **The per-guild channel limit is enforced against the managing edition, NOT entitlement** — the free bot must never publish more than 3 channels, even for an entitled guild whose premium bot hasn't taken over yet. Unlimited channels unlock only once the premium bot is the one actually serving the guild.
- **Channel-limit rejection reasons** — hitting the per-guild channel cap on enable/migrate has three distinct causes, surfaced as distinct CTAs (never one generic error): (1) **free, no subscription** → "Upgrade to Premium" (buy); (2) **entitled, premium bot absent** (never invited or kicked) → "Invite your Premium bot" (re-surfaces the post-checkout invite step they skipped); (3) **entitled, premium bot present but handover pending** → "Premium is activating — grant your Premium bot publish permission in your channels" (points at the handover permission blocker, not an invite). Cases 2 and 3 still enforce the 3-cap until the premium bot is genuinely the worker.
- **Premium handover** — the gated atomic swap from free to premium bot after purchase. Bot permissions don't transfer between Discord applications (the free bot's integration role and its channel overwrites vanish when it leaves), so while both bots are present the premium bot idles (`PremiumPending` marker) and the free bot operates unchanged. The backend evaluates the premium bot's effective permissions across registered channels — measured against the free bot's ACTUAL coverage, so a channel the free bot itself cannot publish in never gates the swap — on join, on permission-change pings, and in the nightly marker sweep (backstop for missed pings); when all pass it flips the marker and has the free bot leave via the free proxy — crossposting and filters cut over atomically. Dashboard warns before the invite and flags blocking channels while pending; pending may last indefinitely (accepted — free keeps covering). If the free bot is kicked mid-pending, premium activates immediately; if the free bot is re-invited while premium is active, the backend makes it leave again.
- **Soft-deleted presence** — kick/leave sets `bot_presence.leftAt` instead of cascading; all guild-scoped config (channels, filters, `migratedAt`, subscription) survives, so an accidental kick + re-invite restores everything (the derived Redis state is rebuilt from DB, entries first, marker last). On re-invite the bot sends the live announcement-channel list from the GUILD_CREATE payload so config for channels deleted while it was away is pruned (missed `channelDelete` events would otherwise leave stale rows consuming free-plan limit slots). A guild with no active presence rows is purge-eligible 30 days after its newest `leftAt` (reconciliation cron, cutoff-guarded so a re-invite landing mid-sweep wins). Mirrors the billing rule "subscription outlives the guild row."
- **Paused channel** — a registered channel that is retained but not currently served, because its guild is over the free channel limit (premium lapsed, or premium bot gone, with >3 registered channels). "Paused" = *system-paused awaiting capacity*, distinct from a user unregistering a channel (which still hard-deletes the row) and distinct from the subscription-scoped `paused` billing status (different entity: a channel is paused, a subscription is paused). Soft-pause via `channel.pausedAt` (nullable timestamp, mirrors `bot_presence.leftAt`): serving iff `pausedAt IS NULL`. **`pausedAt` is set by exactly one thing — the system trim; never by any UI/bot action.** Paused rows keep all config (filters, filterMode) but are absent from the `Channels` Redis allowlist and are NOT counted by the per-guild limit — so the limit counts *serving* channels, not raw rows. **Purely a backend retention mechanism — there is no picker/swap UX.** In the dashboard a paused channel appears in the ordinary Disabled list (`enabled` = row exists AND `pausedAt IS NULL`), carrying only a subtle muted "Saved setup" tag; enabling it is the normal register-or-unpause path (quietly restores its filters, cap-gated), and toggling it off is the normal destructive delete. So a user who *touches* a paused channel (enable→disable) deletes it for good and it will NOT return on re-subscribe — retention protects only channels left untouched after downgrade. Never hard-deleted on downgrade (would violate "restore on re-subscribe"). Real orphans are reaped elsewhere: `channelDelete` removes rows for deleted Discord channels, and the 30-day guild purge cascades all rows once the bot has left — so no time-based paused-channel cleanup exists (a timer would only ever delete live, restorable config). **Enforcement is invariant-driven, not billing-driven** (the Paddle revocation path is untouched): a guild only ever exceeds 3 serving channels while the premium bot is its sole manager (handover completes → free bot leaves), so the invariant "free never serves >3" is violated only when the **free bot (re)enters as manager**. The trim (pause newest excess, keep 3 oldest by `createdAt`) therefore fires on the **free-join rail** (`registerNewGuild('free')` + reconcile free-presence restore), plus a state-based nightly **backstop** (serving-count > 3 → resolve managing edition → trim if free) that also catches the premium-kicked-then-free-invited case and missed joins. Reactivated in bulk when the guild's **managing edition becomes premium** (handover-swap executor / premium sole-manager join) — NOT merely when premium joins, since a pending handover still has the free bot publishing under the 3-cap.
- **Filter** — premium-only message filter (keyword/mention/author/webhook, allow or block mode) attached to a registered channel. Evaluated bot-side per message before fire-to-proxy. Filter data lives in the `Channels` cache JSON value.
- **Publish permissions** — the exact channel permissions a bot needs to crosspost: `ViewChannel` (baseline) + `SendMessages` + `ManageMessages`. Discord's crosspost endpoint requires Send (own messages) plus Manage (others'); `ReadMessageHistory` is NOT required. Canonical definition is `PUBLISH_PERMISSION_FLAGS` in `@ap/utils`, shared by the bot hot path, the bot `/ap` commands, and the backend gate — one source so the three can't drift (they previously checked 2 / 4 / 3 perms respectively).
- **Publish-state cache** — per-channel `{ canPublish, missing[] }` derived from the [[Publish permissions]], **computed by the bot** off its gateway cache (zero Discord REST) and pushed to the backend on the permission events it already handles (`channelUpdate` / `guildMemberUpdate` for `members.me` / `roleUpdate`, batched per guild) plus a full sweep on shard `ready` / `guildCreate`. Stored in a per-guild Redis hash (`publish_state:{guildId}`, DB 13, 14-day safety TTL); the dashboard and the [[Premium handover]] gate read it instead of computing permissions via REST. `getCanPublishMap` (backend REST) survives only as a write-back fallback when a channel's field is missing. The bot is the source of truth; a Redis flush self-heals on the next sweep. See [ADR 0008](./docs/adr/0008-bot-pushed-publish-state.md).

## Billing (Paddle)

- **Paddle** — merchant of record and payment processor for premium subscriptions. See [ADR 0004](./docs/adr/0004-paddle-merchant-of-record.md).
- **Subscription source of truth** — Postgres `subscription` table in this repo's backend, updated by Paddle webhooks. Redis is a possible derived cache, never the owner.
- **Checkout** — a **single unified full-page inline checkout** at the public `/checkout` route (see the Default payment link entry). The backend creates the Paddle transaction (price items + server-set `custom_data: {discord_guild_id, discord_user_id}`, duplicate-subscription guard) and returns the transaction ID; the in-app upgrade flow (subscription panel) then **navigates** to `/checkout?_ptxn={id}&g={guildName}` — the same page every Paddle-sent link lands on — rather than opening an overlay. custom_data is server-set, never client-set (the `g` guild-name query param is cosmetic only — it feeds the on-page "subscribing X" indicator — and is never a trust boundary). Requires a client-side token in web and live-domain approval in Paddle. **Overlay checkout was dropped in favour of one surface**: the inline page reliably renders the collection step that hosts the "Add Tax Number" (business/VAT) option (`showAddTaxId`, default true). [Root cause of the overlay-vs-inline difference is unconfirmed pending a maintainer note — either overlay omitted the option or buried it in its multi-page variant.] **Field collection is entirely Paddle-owned** — no customer PII stored locally (MoR boundary, ADR 0004). Paddle collects the minimum (email + country) by default; full name + address + business/VAT ride the "Add Tax Number" flow onto Paddle's invoice. **The transaction is created WITHOUT a `customerId`** so the checkout always runs its collection step (where "Add Tax Number" lives); pre-binding a customer with a complete address skips collection and hides the business/VAT option (dropped deliberately). Paddle re-links repeat buyers by the email they enter (different email splits them — accepted). No way to force customer-name capture on a plain consumer checkout (accepted — Paddle owns invoice compliance). **Settings passed to `Checkout.open()` are ignored when a `transactionId` is supplied, and the default-payment-link auto-open reads the same `Paddle.Initialize()` settings** — so all checkout behaviour (inline `displayMode`/`frameTarget`, theme, `showAddTaxId`) lives in the Initialize block (`apps/web/src/lib/paddle.ts`, via the parameterized `usePaddle({ onCompleted, onLoaded, settings })` hook). On `checkout.completed` the page redirects to `/dashboard/{guildId}/overview?success=true` (guild id from `custom_data`) — the [[Overview banner stack]]'s checkout-success card is the confirmation (sitting directly above the premium-invite banner it hands off to), Paddle's success screen skipped.
- **Default payment link (`/checkout`)** — Paddle's single configured URL and the app's **one unified checkout surface**. Every customer-facing Paddle link decorates it with `?_ptxn={transactionId}`: abandoned-checkout recovery (`_paction=recovery`), past-due payment-method-update/dunning links (Paddle Retain), and any API-generated `checkout.url`; the **in-app upgrade flow** targets it too (panel navigates to `/checkout?_ptxn={id}&g={guildName}`). Hosted at a dedicated **public** route (never the marketing homepage). The page loads Paddle.js (`initializePaddle`) with **inline** settings (`displayMode: 'inline'` + `frameTarget` container) and renders a `<div class="checkout-container">`; Paddle.js then **auto-opens** the transaction **inline** — the default-payment-link auto-open honors the `Paddle.Initialize()` settings, so no imperative `Checkout.open()` and no per-link special-casing (we act on `_ptxn` only and ignore `_paction`). The `checkout.loaded` event clears the page's loading state; a **server indicator** ("Auto Publisher Premium for {guildName}") reads the `g` query param (in-app flow) and falls back to a neutral label for Paddle-sent links. The optional branded order-summary sidebar is skipped (the inline frame carries the full checkout form). Non-happy paths: no `_ptxn` → redirect `/`; already-paid/expired txn → Paddle.js renders its own overlay error. On `checkout.completed` we read `custom_data.discord_guild_id` (server-set at transaction creation; surfaces on the event, `CheckoutEventsData.custom_data`) and redirect to `/dashboard/{guildId}/subscription?success=true` (the login bump for a logged-out email opener is accepted — fulfillment already happened); absent our IDs (e.g. Retain payment-method transactions) → generic success page. (Redirect target is the guild **Overview** tab — `/dashboard/{guildId}/overview?success=true` — where the checkout-success card now lives, not the Subscription tab.) **Fulfillment is webhook-driven regardless — this page is pure funnel UX.** Must be a Paddle-approved domain, configured separately in the sandbox and production Paddle dashboards (default payment link lives under Paddle → Checkout → Checkout Settings).
- **Subscriber** — the Discord user who paid for a guild's subscription (`subscriberDiscordUserId`, sourced from server-set checkout `custom_data`). A permanent, non-transferable billing role, distinct from guild admin: any MANAGE_GUILD user can see subscription status, but only the subscriber controls billing. If the subscriber becomes unreachable via the dashboard (left guild, lost MANAGE_GUILD, deleted account), nobody takes over — Paddle receipt emails carry portal links, so the payer can always cancel; residual cases go to support.
- **Manage Billing** — Paddle Customer Portal session created by the backend on demand, URL returned only to the subscriber (`portalUrl`). No in-app cancel/payment-method UI is built or maintained. Non-subscriber admins see "Billing is managed by @X" instead of the button — the backend resolves the subscriber's username live via proxy `GET /users/:id` (cached in-memory in the backend ~1h, non-fatal fallback to the raw ID). The subscriber sees the button only (no self-attribution); the API response carries an explicit subscriber field so the panel never infers the role from `portalUrl` presence (a failed portal-session call must not demote the subscriber's view).
- **Duplicate subscription guard** — if a second *entitled* subscription with a different `paddleSubscriptionId` arrives for an already-entitled guild (two admins completed checkout before either webhook landed — the 409 checkout guard only covers transaction creation), `applyPaddleSubscription` keeps the FIRST subscription, ignores the new one, and fires the alert webhook; support cancels+refunds the duplicate in Paddle. Safe because the 409 guard means a legitimate new subscription can only arrive while the existing row is non-entitled (which still overwrites).
- **Entitled** — a guild whose subscription status is `active`, `trialing`, or `past_due`. Local statuses mirror Paddle's five verbatim (`active`, `trialing`, `past_due`, `paused`, `canceled`); `past_due` keeps premium so Paddle dunning can recover the payment. Only `canceled`/`paused` revoke. A stored scheduled change (cancel/pause + effective date) drives "cancels on X" UI.
- **Paddle customer** — the Paddle-side customer entity, resolved by Paddle from the email entered at checkout (one customer per email; one customer can hold subscriptions for multiple guilds). Its ID lands on the subscription row (`paddleCustomerId`) via webhook and is what portal sessions use. Checkout does **not** pre-bind it (see the Checkout entry) — repeat buyers stay one customer only by reusing their email. The Paddle customer `name` is customer-owned and customer-facing (checkout, invoices, portal) — never encode Discord IDs in it; Discord linkage lives in subscription `custom_data`.
- **Plan catalogue** — one Paddle product ("Auto Publisher Premium"), two prices: $4.99/month, $49.99/year. No trial period; money-back requests are Paddle refunds. Price IDs are backend-only config (backend creates the transaction), not `NEXT_PUBLIC_*`.
- **Subscription outlives the guild row** — `subscription` has no cascading FK to `guilds`. Kicking the bot or deleting the server never deletes or cancels the subscription (kick is often accidental; re-invite restores premium instantly). The subscriber cancels via dashboard/portal; the dashboard can show a subscription for a server the bot is no longer in.
- **No per-transaction invoicing export** — the old HMAC invoicing forwarder (`invoicing.ts`) is deleted. Paddle (MoR) issues customer invoices; company bookkeeping runs off Paddle payout statements.
- **Revocation** — a `canceled`/`paused` webhook makes the backend have the premium bot leave the guild (via the premium proxy), but **only when the premium bot is actually present** (`Editions.isBotPresent(guildId, 'premium')` — a cheap `bot_presence` read); a subscribed-but-uninvited or already-departed guild is a no-op, so no Discord call is made. This matters for the invalid-request budget: `DELETE /users/@me/guilds/:id` is rate-limited to 1/window with `scope: user` (non-shared), so a pointless leave collides on that bucket and the resulting 429 counts toward the Cloudflare ban budget (the `10004 Unknown Guild` 404 itself does not count). `leaveGuild` treats `10004` as success — "bot is not in the guild after this call" is true whether we removed it or it was already gone — so the handover swap's leave-failure alert only fires on real failures. Skipping a leave because presence is stale-absent is backstopped by the nightly guild reconcile (restores presence) followed by the subscription reconcile (`getRevokedWithBotPresent` re-revokes). The entitlement gate is backend-side in `registerNewGuild` (ADR 0006) — the bot has no subscription check; that gate's leave is NOT presence-gated (it fires exactly when the bot just joined and is present, before any presence row is written). A daily reconciliation cron lists subscriptions from the Paddle API and repairs Postgres drift (missed webhooks); it replaces the hourly local `currentPeriodEndsAt` expiry scan — Paddle owns period-end cancellation.

## Dashboard

- **Guild Overview tab** — the guild dashboard's **attention surface** and default landing tab: `/dashboard/:guildId` redirects to `/overview` (was `/channels`), so opening a guild shows banners + status first. Hosts the guild-scoped banner stack (moved off the shell — see [[Overview banner stack]]) plus a read-only **channel status** section. Status is **permission-derived from existing data only** (the [[Publish-state cache]], ADR 0008) — no publish-activity feed or rate-limit counters are plumbed to the web. Migrated guild: itemized list, each enabled channel shown as *publishing* (`canPublish === true`), *needs permissions* (`canPublish === false`), or *paused* (`hasSavedSetup`), under a heading that names the attention count ("2 need attention"); the list is **read-only** (no toggles — Channels tab stays the sole place to enable/disable; each flagged row links there). Healthy migrated guild (no banners, nothing to fix): a positive "All good — publishing in N channels" header above the full (all-green) list. Legacy guild: **no itemized list** — just a minimal "publishing in N of M channels" summary under a prominent migrate banner (steer to migrate before per-channel detail). A small **persistent info callout** in the status header states Discord's 10-published-messages/hour/channel limit (informational only — we surface no live counter).
- **Overview banner stack** — all guild-scoped banners render **only inside the Overview tab** (reverses the old shell-hosted, nag-everywhere placement — pages and the shell no longer render guild-level banners; see ADR 0010). Order (top → bottom): (0) **checkout success** (green, query-param-scoped on `?success=true`; the post-checkout redirect now targets `/dashboard/:guildId/overview?success=true` so the card and the premium-invite banner it hands off to sit together), (1) **premium invite needed** (`hasSubscription && !premiumBotPresent`, purple), (2) **premium pending** (purple; mutually exclusive with invite), (3) **legacy migration** (amber, → migrate modal), (4) **paused channels** (yellow, dismissible). Banners 1–3 stay non-dismissible; paused stays the lone dismissible exception (episode-scoped `localStorage` marker per `guildId`, ADR 0009). Off-tab, the only persistent signal is the [[Overview attention badge]].
- **Overview attention badge** — a count on the Overview sidebar item, visible on **every tab within a guild's dashboard** (computed client-side in the shell from `useGuild()` context — zero new data; scoped to the guild dashboard, NOT the server-list page, whose payload lacks channel-level `canPublish`). Counts **distinct attention items**: each active banner = 1 (premium invite, premium pending, legacy migration, and paused **only while not dismissed**), **plus 1** if ≥1 *enabled* channel needs permission fixing (managing bot `canPublish === false`). The positive checkout-success card never counts. Premium-handover access gaps (`premiumBotHasPermissions === false`) are **not** a permission-fixing item — they are owned by the premium-pending banner (the free bot is still publishing), so they never double-count. Legacy guilds add no per-channel permission item (migration comes first). Badge hidden entirely at 0. It is the mitigation for banners no longer nagging on every page.
- **Bot invite (server list)** — a bot-absent guild card in the dashboard server list is a Discord OAuth invite link (new tab, `guild_id` pre-selected, guild dropdown left **open** so the user can pick a different server). The post-payment "Invite Premium Bot" button (subscription panel) is the exception: it keeps `disable_guild_select` because the invite is tied to the subscribed guild — the premium entitlement gate would make the bot self-leave anywhere else. Edition rule: invite the **free** bot, unless the guild has an entitled subscription — then invite the **premium** bot (premium without a subscription is pointless — the entitlement gate makes it leave; free with a subscription wastes the subscription). Client IDs are env-sourced per deployment (`NEXT_PUBLIC_FREE_BOT_CLIENT_ID`, `NEXT_PUBLIC_PREMIUM_BOT_CLIENT_ID`) — never hardcoded: a baked-in production ID once made local dev invites authorize the prod bot, so local presence never updated. If the premium ID is unset, fall back to the free invite; if the free ID is unset, the card renders non-clickable. After an invite click (server list or subscription panel), the page re-fetches once on the next window focus (one-shot — `/users/@me/guilds` is rate-limited per user token, so no refresh on ordinary tab switches, and no retry polling: returning before the bot's `guildCreate` lands shows stale presence until manual reload — accepted).
- **Locked premium tab** — premium-only dashboard tabs (currently only Filters; more planned) are always visible rather than hidden — a deliberate reversal of hiding, for discoverability/upsell. Marked in the sidebar with a trailing right-aligned crown (`ml-auto`) that inherits the tab's text color and turns yellow on hover (`group-hover:text-yellow-500`), shown for **all** servers (crown = "premium feature"; a premium server owns it, a free server can't use it yet — the sidebar does not encode locked-vs-active; the page does). A free server's premium route no longer redirects away; it renders the shared presentational `<LockedFeature>` component (crown hero + feature-specific benefit copy + "Upgrade to Premium" CTA that routes to the Subscription tab — the sole checkout source of truth, never a second Paddle overlay). Gate is per-page (`isPremium = premiumBotPresent || hasSubscription`, reused verbatim, frontend-only); `<LockedFeature>` is presentational, not a gating wrapper. Adding a premium tab: flag it `premiumOnly` in the sidebar `tabs` config (gets the crown automatically) and render `<LockedFeature>` with its own copy when `!isPremium` — copy stays local to each feature page, shell stays shared.
- **Dashboard read caching** — the dashboard is Discord-REST-bound, not DB-bound, so caching lives in two layers, never in the query layer (ADR 0007). (1) **Backend in-memory** `cachedGet(route)` over the three per-guild bot-scoped GETs (`/guilds/:id/channels`, `/roles`, `/members/:botId`), **keyed by route only** (5-min TTL, in-memory not Redis — single-instance backend, TTL self-evicts). `/channels` and `/roles` are guild-global (Discord returns all regardless of the fetching bot's perms), so one shared entry per guild across editions; `/members/:botId` self-namespaces by botId. Miss fetched via a present edition; only 200s cached. Retires `LegacyGuildPerms` (the `canPublish` map recomputes free from the cached raw roles+member). The composed `/api/guild/:guildId` still reads Postgres/Redis live, so web mutations reflect instantly. (2) **Web** — no cross-request cache. The guild payload is **not** cached in the shared Next.js Data Cache: `/api/guild/:guildId` authorization is per-user and enforced in the backend (`requireGuildPermission`, `MANAGE_GUILD`, 60s-cached per token), so a shared server cache in front of it would bypass authz and expose a guild to any logged-in user — every guild load hits the backend and authz runs each time. Warm loads are fast anyway (Lever B serves Discord data; the authz check is 60s-cached). Invalidation is TTL-only for **permission** data (roles / bot member / `canPublish`) — no permission-ping eviction (would burn the REST budget in high-churn guilds). The **channel list** is the one exception: actively evicted when the bot sees a channel created / deleted / cross the `GuildAnnouncement` type boundary, so a new [[Candidate channel]] appears (and a deleted one disappears) without the 5-min wait — a narrow, low-frequency trigger, deliberately NOT routed through the high-churn permission-sync path (ADR 0007 amendment). Everything edited in the dashboard reflects instantly (live Postgres/Redis reads); only Discord-derived permission data is ≤5 min stale. Instant back-navigation to an already-opened guild comes from Next.js's client Router Cache (`experimental.staleTimes.dynamic = 60`, per-browser, busted by the mutations' existing `router.refresh()`) — not a client-caching library.
- **Sidebar order** — the dashboard channels list mirrors Discord's sidebar, not the raw API response (`GET /guilds/:id/channels` is unordered, and `position` is scoped per category — two channels in different categories can share a position): uncategorized channels first, then categories by their position, channels within a category by `position`, ties by snowflake id ascending (Discord's own tiebreak). Sorted backend-side in `GET /api/guild/:guildId` where the full channel list (incl. categories) is in hand before the announcement-type filter drops them — the API contract is "channels arrive in sidebar order"; the web only preserves array order (enabled/disabled sections each stay internally ordered). No category labels in the UI; `/ap status` (DB-only path, no position data) stays unordered.

## Ops

- **Alert webhook** — Discord webhook (`ALERT_WEBHOOK_URL`) for events where a human should act, sent via a fire-and-forget `sendAlert(key, ...)` helper in a dedicated `@ap/alerts` package (send failure only logs, never fatal; `@ap/logger` stays Redis-free). Repeat firings of the same key are throttled via the `Alerts` Redis DB (30 min TTL), so it works across processes and restarts. Message format: one minimal embed — title = event name, description = details, timestamp, fixed color, footer = service + edition; no severity taxonomy. Wired events: duplicate entitled subscription (cancel+refund in Paddle), guild-presence reconcile rails tripped (pagination abort / deletion cap), proxy invalid-request self-shed activation. Deliberately excluded: crosspost queue high-water (fatigue risk during Discord outages). Bar for adding events: actionable, not merely unusual.

## Services

- **bot** — discord.js gateway listener, one instance per edition (separate Discord applications/tokens). Multi-shard via discord-hybrid-sharding. Owns no Discord REST traffic on the hot path (gates everything synchronously, fires-and-forgets to its edition's proxy). Does sync permission checks against discord.js cache (never `.fetch()`).
- **backend** — internal Express API, **single instance serving both editions** (edition-agnostic: no `APP_EDITION`; Paddle always configured — ADR 0006). Owns channel registration, filter CRUD, Paddle subscriptions, bot presence, the premium entitlement gate, handover orchestration, guild migration markers, the public `/api/*` web surface, and the `Channels` Redis cache. Holds both bot tokens; routes Discord REST through the managing edition's proxy; the backend is the single orchestrator of all bot join/leave decisions.
- **proxy** — see Crosspost pipeline above; one instance per edition, each with its own egress IP (Cloudflare ban isolation — Discord rate limits are per token, the IP only matters for the invalid-request ban).
- **web** — Next.js dashboard. Reads from the single backend's `/api/*` (one `BACKEND_URL`).

## Key architectural rules

- **Be conservative with Discord REST calls — always.** The hard ceiling is the Cloudflare invalid-request ban (10k 401/403/non-shared-429 per 10 min per egress IP; proxy self-sheds at 5k), and several routes are per-token/per-user rate-limited to 1/window. Treat every Discord REST call as scarce budget: dedup calls (never fetch the same resource twice in one request), prefer cache/DB-derived state, gate calls behind presence/relevance checks so no call is made when the answer is already known, and never add speculative or polling calls. When designing a feature, the default question is "can this avoid a Discord call?" — see ADR 0007 (dashboard caching favours TTL over active eviction for exactly this reason) and the `Revocation` entry (leaves are presence-gated to avoid pointless 429-generating calls).
- **Bot never `.fetch()`s on the hot path.** `members.me` is auto-populated by `GUILD_CREATE`; trust the cache. Permission checks use `permissionsFor` only.
- **Bot's REST = proxy's REST.** Bot's discord.js is configured with `api: '{this edition's proxy}/api'` (`config.proxyUrl`) and `globalRequestsPerSecond: Infinity` (proxy is the global limiter).
- **Crossposts are never dropped on transient errors.** Route 429s are absorbed by discord.js internally. Sublimit (long waits), global 429s, 5xx, and network errors all become BullMQ delayed retries. Only `already_done`, `blocked`, `sublimit-lock`, and `fatal_4xx` are intentional skips.
- **Single REST instance per token.** One `@discordjs/rest` handles crosspost queue worker and `/api/*` passthrough. Global ceiling is `50/s`; interactions use `BurstHandler` so they don't compete with crossposts.
